PHASE 3 — SELECT THE CORRECT CHAPA INTEGRATION MODEL
====================================================

Use Chapa's standard/hosted transaction initialization flow unless the existing architecture contains a legitimate reason to use another officially supported method.

Preferred model:

1. User fills donation form.
2. Backend validates the request.
3. Backend creates a local donation record.
4. Backend creates a unique payment attempt and unique Chapa transaction reference.
5. Backend calls Chapa's transaction initialization API using the server-side secret key.
6. Backend persists the provider response needed for the payment flow.
7. Backend returns ONLY the safe checkout information required by the browser.
8. Browser redirects to the Chapa checkout page.
9. Chapa processes the payment.
10. Chapa redirects/callbacks to the application.
11. Backend verifies the transaction against Chapa.
12. Chapa webhook is independently verified and processed.
13. Database state is updated atomically.
14. Frontend retrieves authoritative status from the backend.
15. Donor sees the final state.

Do NOT collect raw card credentials in the church website unless there is a compelling, documented requirement and the official Chapa documentation confirms the exact flow.

Do NOT put the Chapa secret key in:

* React components
* browser JavaScript
* NEXT_PUBLIC_* variables
* HTML
* client bundles
* source maps
* logs
* error responses

Only server-side code may access the secret key.
